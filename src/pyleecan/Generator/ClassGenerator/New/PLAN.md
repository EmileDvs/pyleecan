# Pyleecan class refactoring plan

Status of the migration from the legacy CSV-generated classes to modern Python
class models. Branch: `switch_to_dataclass`. Last update: 2026-11-15.

Working rules: one commit per increment; each new generator feature gets small
unit tests; the older generator tests (`Tests/New/test_*.py`) are run for the
final validation only.

## Goal

Pyleecan classes are today generated from CSV files (`Generator/ClassesRef`) into
hand-rolled classes with custom setters, type checks and parent links. The new
release replaces them with classes built on standard libraries:

- **pydantic v2** models (reference implementation),
- **stdlib dataclasses + dacite** (alternative implementation, kept to compare).

The migration is done in two phases:

- **Phase 1 (current scope):** a new generator produces both implementations from
  the legacy sources. They are validated against the legacy classes: same
  defaults, same serialization, same method results. Legacy behaviours are kept
  in a dedicated compatibility layer.
- **Phase 2 (later):** the CSV files and the legacy compatibility layer are removed.
  The class definitions become the single source of truth, and the tests are
  aligned on the runtime class metadata (`ClassInfo`).

## Target layout

```
Classes/             legacy classes (reference, not modified)
Classes_new/         dataclass + dacite implementation   ─┐ generated by one class
Classes_pydantic/    pydantic implementation (reference) ─┘ generator (backend option)

Functions/           legacy functions (not modified)
Functions_new/       functions using Classes_new         ─┐ generated by the
Functions_pydantic/  functions using Classes_pydantic    ─┘ functions generator

Methods/             legacy methods (not modified)
Methods_new/         hand-written methods, shared by both implementations
```

Generated folders are never edited by hand: changes go in the generators
(`Generator/ClassGenerator/New/`) and the affected classes are regenerated.

Exception: `Functions_new` is bootstrapped one legacy package at a time, like
`Methods_new`. A bootstrapped module becomes hand-written and is no longer
overwritten. `Functions_pydantic` is always generated from `Functions_new` by
import rewriting only, so there is a single hand-written function source.

### Class sub-packages

`Classes_new` and `Classes_pydantic` are organized in sub-packages, following
the legacy packages (`Generator/ClassesRef`), with snake_case lowercase names
(PEP 8). The physics modules are taken out of `simulation` into their own
sub-packages, together with their child classes.

```
Classes_new/                 (same tree in Classes_pydantic/)
    _import.py, _class_info.py, ...     shared support modules stay at the root
    _smoot/, _swat_em/                  vendored code stays at the root until Phase 2
    converter/       6 classes
    elmer/           5 classes   Elmer, ElmerResults, ElmerResultsVTU, Section, SolverInputFile
    geometry/       12 classes
    gui_option/      2 classes   legacy "GUI_Option"; GUIOption.csv says "GUIOption"
    import_data/    14 classes   legacy "Import": `import` is a Python keyword
    loss/           10 classes
    machine/        49 classes
    material/       11 classes
    mesh/           22 classes
    optimization/   11 classes
    output/         17 classes   includes OutElec, OutMag(FEMM/Elmer), OutForce, OutStruct
    post/            5 classes
    scidatatool/    16 classes
    slot/           59 classes
    simulation/     25 classes   Simulation, Simu1, Input*, OP*, VarSimu*, ParamExplorer*, ...
    electrical/      8 classes   Electrical, ElecLUTdq, EEC, EEC_LSRPM, EEC_PMSM, EEC_SCIM,
                                 Drive, DriveWave (unused today, kept for later)
    magnetics/       3 classes   Magnetics, MagFEMM, MagElmer
    force/           3 classes   Force, ForceMT, ForceTensor
    structural/      3 classes   Structural, StructElmer, Mode
```

Taken out of the legacy `Simulation` package: the physics modules with their
child classes, plus `Drive`/`DriveWave` (electrical) and `Mode` (structural).
`Mode` still inherits `SolutionMat`, from `mesh`: inheritance across
sub-packages is allowed.

- The module name inside a sub-package is unchanged (`geometry/arc_1.py`), and
  stays unique across sub-packages.
- Sub-package `__init__.py` files do not import their classes, to avoid import
  cycles and slow imports; classes are imported from their module.
- `_package` keeps the legacy package name during Phase 1 (`ClassInfo` is checked
  against the CSV files); the new location is given by the module path. Phase 2
  drops `_package`.
- `Methods_new` follows the same sub-packages (`Methods_new/magnetics/MagFEMM/`).
- `Functions_new` and `Functions_pydantic` keep the legacy `Functions` folders.

### Class bases

Each implementation has two levels of base class:

| | Dataclass (`Classes_new`) | Pydantic (`Classes_pydantic`) |
|---|---|---|
| Target base (Phase 2 design) | `PyleecanClass` | `PyleecanModel` |
| Legacy layer (Phase 1 only) | `LegacyClass(PyleecanClass)` | `LegacyModel(PyleecanModel)` |

During Phase 1, the generated root classes inherit from the legacy layer. Phase 2
switches them to the target base and deletes the legacy layer. The generator
names this base in a single place.

| Behaviour | Target base | Legacy layer |
|---|---|---|
| Type, min and max validation, on init and assignment | ✅ | |
| `__class__` written on dump and read on load (polymorphic objects) | ✅ | |
| ndarray-aware equality | ✅ | |
| Native types: `complex` (int and float accepted), minimal `NDArray` | ✅ | |
| `None` accepted by every field | | ✅ |
| `-1` sets the default value | | ✅ |
| `as_dict` legacy format (complex as str, `type_handle_ndarray`), `from_dict`, `copy`, `compare` | | ✅ |
| Unknown keys ignored on load (old files) | | ✅ |
| Parent links (`obj.parent`) | | ✅ |

### Shared support modules

Modules that do not depend on the implementation (class import, `ClassInfo`
metadata, errors, checks) are written once in the `pyleecan/classes_common`
package (lowercase, PEP 8) and used by both `Classes_new` and
`Classes_pydantic`; the lookup and `ClassInfo` take the class package as a
parameter. Only the base classes differ per folder.

## Decisions

| Decision | Choice |
|---|---|
| Reference implementation | pydantic; the dataclass implementation is kept and compared |
| Class folders | `Classes` (legacy), `Classes_new` (dataclass), `Classes_pydantic` (pydantic) |
| Legacy compatibility | in a separate layer (`LegacyClass`/`LegacyModel`) above the target bases |
| Parent links | removed from the target design; kept only in the legacy layer |
| Reworked methods | hand-written `Methods_new` folder, read by the generator instead of legacy `Methods` |
| `Methods_new` bootstrap | one legacy package at a time, copied when its refactor starts; the generator falls back to legacy `Methods` for the others |
| Test layout | one test tree, run against each implementation with `pytest --backend=dataclass\|pydantic` |
| Support modules | shared between implementations |
| Type hints | completed in `Methods_new` and the bootstrapped `Functions_new` modules (Phase 1), checked by a type checker |
| Class-specific functions | functions that depend on a single class's meaning or data become methods of that class (Phase 1) |
| Class organization | sub-packages following the legacy packages, lowercase; electrical, magnetics, force and structural taken out of simulation (Phase 1, Step 0) |
| Repository layout | Python packaging standards, applied in Phase 2 (see below) |
| smoot, swat_em | vendored unmodified under `pyleecan/_vendor/` (Phase 2) |
| SciDataTool | a pyleecan subpackage sharing the class system; no longer a separate library (Phase 2) |
| Executable | `Exe_gen` replaced by a uv-based release script (Phase 2) |

### Why the parent links are removed

Parent links (`self.parent`) let a child object read its container, for example
a slot reading the bore radius of its lamination. They are removed from the
target design because they:

- create reference cycles that copy, equality and serialization must work around;
- need generated parent-type rules, checked on every assignment;
- break silently: an object put in two containers, or copied, loses its context;
- hide the real inputs of a method: `slot.comp_height()` depends on the lamination
  without saying so.

Methods receive their context explicitly instead, for example
`slot.comp_height(lam)`, or the method moves onto the container.

## Steps

### Step 0: separate the implementations in the generator

- [ ] Replace the per-package pydantic switch with a `backend="dataclass"|"pydantic"`
      option that also selects the output folder.
- [x] Write the classes into their sub-package (see Class sub-packages): legacy
      package mapped to its lowercase name, plus the moved physics classes.
- [x] Runtime class lookup by name (`import_class`, for serialized `__class__`)
      and `ClassInfo` walk the sub-packages; no generated lookup table.
- [x] Class, function and test generators write the new module paths in imports.
- [x] Regenerate `Classes_new` in the new sub-packages (commit 4e9e7fac4;
      `Tests/New/Classes` identical to the baseline; unit tests in
      `Tests/New/test_class_subpackages.py`).
- [ ] Regenerate `Classes_new` entirely as dataclasses (Geometry included).
- [ ] Generate `Classes_pydantic`. It imports the vendored code (`_smoot`,
      `_swat_em`) from `Classes_new` instead of generating a third copy.
- [ ] Declare `pydantic>=2.12` (and `dacite`) in `pyproject.toml` / `uv.lock`.

### Step 1: split the bases

- [ ] Create the shared support module.
- [ ] Create `LegacyClass` and `LegacyModel`; move the legacy behaviours there.
- [ ] Slim the target bases; use native `complex` and a minimal `NDArray` in `PyleecanModel`.
- [ ] Contract tests for the target bases: one behaviour specification that
      both implementations must pass (accepted inputs, errors, serialization).

### Step 2: type, min and max validation for dataclasses

- [ ] Validate in `PyleecanClass.__setattr__`, which also covers `__init__`, from
      the resolved annotations (cached per class) and the min/max field metadata.
- [ ] Target: `Tests/New/Classes/test_classes.py` passes. Baseline on 2026-11-15:
      453 failures, all type/min/max (`test_class_type_float` 240,
      `test_class_min` 143, `test_class_max` 70).

### Step 3: `Functions_pydantic`

- [ ] Add the backend option to the functions generator (class imports,
      load/save, retrocompatibility).

### Step 4: Phase 1 test architecture

- [ ] `--backend` option: the generated `Tests/New` tree imports the classes
      through an alias package that `conftest.py` maps to `Classes_new` or
      `Classes_pydantic`.
- [ ] Parity tests: the legacy-derived suite passes on both implementations.
- [ ] Cross tests: legacy, dataclass and pydantic objects built from the same data
      give the same `as_dict`, load the same files and give the same method results.
- [ ] CI runs the suite once per backend.

### Step 5: package refactor pass (`Methods_new`)

Each legacy package is refactored in a single pass, so it is opened, reviewed
and validated once:

1. Bootstrap: copy the package's legacy methods into `Methods_new`, and its
   functions into `Functions_new` (now hand-written).
2. Remove the parent reads (see below).
3. Move the class-specific functions into their class.
4. Complete the type hints.
5. Type check, then run the parity tests.

#### Parent links

Parent reads found in the methods on 2026-11-15:

| Package | Parent reads | Classes | Typical use |
|---|---|---|---|
| Geometry | 0 | 12 | none |
| Slot | 261 | 56 | slot or hole reads its lamination (`Rint`, `Rext`, `get_Rbo()`, `is_stator`, `get_label()`) |
| Machine | 142 | 19 | winding, conductor and end winding read the slotted lamination; bore and notch read the lamination |
| Simulation | 118 | 25 | a model reads the simulation, then the output (`self.parent.parent`) |
| Loss | 38 | 9 | loss models walk up to the machine or output |
| Output | 25 | 5 | sub-outputs read the `Output` |
| Optimization | 4 | 2 | |
| Functions | 3 files | | `check_parent`, `assign_femm_surface`, `get_logger` |

These reads follow five patterns, each solved once:

1. A child reads its container's data: pass the container as an argument, or move
   the method onto the container.
2. A simulation model walks up to the simulation and output: pass the context
   explicitly (`run(output)`).
3. Labels (`self.parent.get_label()`): the caller passes the label.
4. Navigation helpers (`get_machine_from_parent`, `check_parent`): explicit arguments.
5. The logger chain (`get_logger` walks the parents to find a `logger_name`;
   175 calls in 51 files): replace it with per-module loggers or a context
   logger set by `Simulation.run`.

#### Class-specific functions

A legacy function moves into a class when it depends on that class's meaning or
data, not merely because a single class calls it today. A generic helper such
as `circle_from_3_points` stays a utility even though only `SlotCirc` uses it.

- A function taking the object as first argument becomes a regular or private
  method; `@staticmethod` is only for functions that do not use the object.
- Heavy optional dependencies (FEMM, gmsh, pyvista) stay imported inside the method.
- The old function path is kept as a deprecated alias until Phase 2, for user
  scripts and tutorials.
- SciDataTool internals are out of scope.

First audit (2026-11-15, from imports): 26 of the 145 legacy `Functions` modules
are used by a single class, for example `comp_FEMM_torque` and
`build_meshsolution` (`MagFEMM`), `get_area` (`OutMag`), `cut_lines_between_angle`
(`Bore`). Another 41 modules are imported by no class, function or GUI module.

#### Type hints

Coverage on 2026-11-15: 49 of the 1823 legacy method functions and 11 of the 450
legacy functions are fully hinted.

- Draft hints are produced from the numpydoc `Parameters`/`Returns` sections, then
  reviewed.
- Class annotations use `from __future__ import annotations` and imports under
  `if TYPE_CHECKING:`, so they add no runtime import (no cycle, and the import
  rewriting between backends keeps working).
- A type checker (pyright basic mode, or mypy) runs on the refactored packages
  only, made stricter step by step. A `py.typed` marker publishes the hints.

- [ ] Simulation, Loss, Output, Optimization
- [ ] Logger chain
- [ ] Functions helpers (`check_parent`, `assign_femm_surface`, `get_logger`)

## Phase 2: repository layout

Done after Phase 1, with the removal of the legacy code, to follow Python
packaging standards.

| Today | Target | Note |
|---|---|---|
| `Tests/`, with `Tests/New` | `tests/` at the repository root | `Tests/New` becomes `tests/` once legacy is removed |
| `Classes`, `Functions`, `GUI`, ... | lowercase package names (`classes`, `functions`, `gui`) | PEP 8; breaks user imports: release note, possibly one release of aliases |
| class-independent functions | `src/pyleecan/utils/` | |
| `src/pyleecan/Generator` | removed | the classes become the source |
| `Classes/_smoot`, `Classes/_swat_em`, their `Functions` parts and copies | `src/pyleecan/_vendor/smoot/`, `src/pyleecan/_vendor/swat_em/` | unmodified, with `LICENSE` (BSD-3, MIT) and a `VENDORED.md` (source fork, commit, local patches); imported, not generated |
| SciDataTool classes, methods and functions | `src/pyleecan/scidatatool/` | a pyleecan subpackage sharing the class system |
| `src/pyleecan/Results` (104 MB), `src/pyleecan/tmp` | outside the package (user folder; `tmp_path` in tests) | could be done earlier: cheap and independent |
| `src/pyleecan/Data` | `src/pyleecan/data/`, read with `importlib.resources` | package data |
| `Doc`, `Tutorials` | `docs/`, `examples/` | |
| `pytest.ini`, `.pylintrc`, `tox.toml` | `pyproject.toml` (`[tool.pytest.ini_options]`, `[tool.ruff]`, type checker) | ruff replaces pylint |
| `Exe_gen/` | `tools/exe/` | see below |
| none | `CHANGELOG.md`, `CONTRIBUTING.md` | the changelog carries the release notes |

Vendored code is installed under the `pyleecan` namespace, not as top-level
packages: top-level `smoot`, `swat_em` or `scidatatool` packages would clash with
the original projects installed in the same environment.

### Executable

uv does not build executables, but it replaces most of the legacy
`generate_pyleecan_exe.py` (clone, virtual environment, requirements):

- `uv sync --frozen`, then `uv run --with pyinstaller pyinstaller pyleecan.spec`.
- The `.spec` is rewritten: no hardcoded `site-packages` paths (covered by
  `pyinstaller-hooks-contrib`), no `Class_Dict.json`, hidden imports updated to
  the new package names.
- The Inno Setup script (`pyleecan.iss`) and the icon are kept; the version is
  read from `pyproject.toml`.

## Challenges

- **Generating every class with pydantic.** Only Geometry has been validated so
  far. Other packages use types not yet tried with pydantic (function fields,
  SciDataTool objects, dicts of objects, vendored packages). Packages are
  switched in order (Geometry, Slot, Machine, ...) with a parity check at each step.
- **Same behaviour for both implementations.** Errors (`ValidationError` against
  `CheckTypeError`) and lax conversions (int to float, list to ndarray, numpy
  scalars) must be specified once, in the contract tests, so the
  implementations do not drift.
- **Parent removal changes method signatures.** Tests derived from the legacy
  tests no longer apply to a refactored package. Its tests become hand-maintained,
  and parity is checked on numerical results (legacy `slot.comp_height()` against
  new `slot.comp_height(lam)`). This is why Step 5 comes after the API-identical
  parity of Steps 0–4.
- **`Methods_new` code must suit both implementations:** keyword arguments (pydantic
  models are keyword-only), no parent reads, no `-1`/`None` conventions.
- **Bootstrapped and generated modules side by side in `Functions_new`.** The
  functions generator needs an explicit list of the bootstrapped modules, so it
  never overwrites hand-written code.
- **Moving functions into classes changes import paths.** Deprecated aliases
  keep user scripts working until Phase 2.
- **Class lookup without a generated table.** A serialized `__class__` gives a class
  name, not its sub-package. `import_class` finds the module by walking the
  sub-packages for `class_module_name(name)`, cached after the first lookup.
- **Nullable fields.** The CSV files do not say which fields can really be `None`,
  so "None everywhere" stays in the legacy layer until Phase 2 types fields as
  `X | None` where needed.
- **GUI.** The legacy GUI relies heavily on parent links. It is not migrated yet
  and is out of scope of this plan.
